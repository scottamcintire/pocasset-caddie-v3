## 2. Keeping V3 completely isolated

### Folders, repositories, sites

| | Production (frozen) | V3 development |
|---|---|---|
| Mac folder | `Documents/Pocasset AI Caddie/…` | `Documents/Pocasset_Caddie_V3` (new) |
| GitHub repository | `pocasset_caddie` | `pocasset-caddie-v3`, **not created until you approve** |
| Website | …github.io/pocasset_caddie/ | …github.io/pocasset-caddie-v3/, **not published until you approve** |

### Browser storage: the real risk, and how V3 avoids it

Every GitHub Pages site under `scottamcintire.github.io` is the **same browser origin**. They all share:
- localStorage
- IndexedDB
- the cache storage
- location permission

Only service-worker *scopes* are separated, by path.

Keys and caches in use today:

| Used by | Keys / caches |
|---|---|
| V2.3.1 and V2.2.1 | localStorage `pocasset_caddie_v1` (your round), `pocasset_pins_v1` (today's pins) |
| greens-test | localStorage `pocasset_greens_test_v1` |
| V2.3.1 service worker | cache `pocasset-caddie-<hash>` |
| greens-test service worker | cache `pocasset-greens-<hash>` |

**A concrete hazard I found:** whenever the V2.3.1 service worker updates, it **deletes every cache whose name starts with `pocasset-caddie-`**. A V3 cache named `pocasset-caddie-v3-…` would be wiped by production. V3 avoids this with the following rules:
- **One prefix for everything:**
  - storage keys are prefixed `pocasset_v3:`
  - cache names are prefixed `pcv3-`, which neither existing service worker touches
  - V3's own service worker only ever deletes `pcv3-` caches
- **Only one storage module can write.** It refuses any key without the V3 prefix.
- **Importing a V2 round or pins is an explicit button.** It reads V2's data, copies it into V3 and never writes back.
- **The V3 service worker** lives at `/pocasset-caddie-v3/sw.js`. Its scope cannot overlap `/pocasset_caddie/`, because the paths differ (`_` versus `-`).
- **An automated isolation test** snapshots every non-V3 key and cache, runs the whole V3 test suite, and fails if anything outside V3 changed.
- **Optional, for full separation later:** give V3 its own origin with a custom domain. It isn't needed if the rules above are kept.

### Version history and rollback
- V3 has its own git history from day one. It is a local repository now, and pushed only after you approve.
- Each approved milestone gets a git tag (`v3.0.0-hole02-proto`, …) and a dated zip in the Mac folder.

### Accuracy warning: the course was recently rebuilt
- Mass Golf (Aug 2026) reports that Pocasset "completed a comprehensive restoration that included the reconstruction of every bunker and tee", plus green-site enhancements. Source: massgolf.org, *Pocasset Selected To Host 118th Massachusetts Open*.
- The OSM bunkers on Hole 2 were all drawn in one batch.
- **I cannot tell whether they show the bunkers before or after the rebuild.**
- No bunker, and no bunker distance, should be trusted until checked.

### How we verify, cheaply
1. **Aerial check (at home).** I made `data/holes/hole02/hole02_check.kml`.
   - Open it in Google Earth Pro and compare the outlines with the newest imagery; the History slider shows the photo date.
   - A bunker that doesn't match its outline gets flagged.
2. **Field check (on the course).** A V3 test page records your phone's GPS at a few bunker edges.
   - The difference from the map, in yards, is logged.
   - It needs the V3 site published, so it waits for your approval.

### Sources for what's missing (all public and free; downloading them needs your Mac or you)
- **Elevation:** USGS 3DEP lidar, 1 m bare-earth elevation. Massachusetts has 3DEP lidar statewide; the Barnstable County 2010 collection is 1 m. It is public domain.
- **Trees:** two options:
  - **Lidar canopy height** (surface minus bare earth) shows where trees actually stand.
  - **MassGIS 2016 land cover** (1 m, from aerial imagery) has a tree class, but it is from 2016.
- **OSM woods and tree rows** around the course are not in our file. They would need a fresh OpenStreetMap extract, which my workspace cannot reach.

**Other sites checked:**
- OpenYardage builds yardage books from OpenStreetMap, so it carries the same data, not new data.
- The zommagolf and openyardage pages themselves were not reachable from my workspace.
- Commercial maps (GolfLogix, ezLocator) are not licensed for reuse.

**Licensing consequence:** if V3 publishes data derived from OSM (outlines or bunker coordinates), the site must credit "© OpenStreetMap contributors". Under ODbL share-alike, the course *database* we derive from it must stay under ODbL. Our app code and artwork can keep their own licence. *(I'm not a lawyer; this is the standard reading of the ODbL.)*

**Hole 2 verdict:**
- Enough to build a **geometry-true prototype** of tee, fairway, pond, greenside bunkers, green and cart path.
- **Not enough to call it accurate** until the bunkers and tees are checked against post-rebuild imagery or on the course.
- Trees and elevation are missing until the lidar is downloaded. Without them, trees are left out rather than invented, and the ground is drawn flat.

## 4. How to make flyovers that are both beautiful and true

| Approach | Looks | Geographic truth | GPS markers line up? | iPhone cost |
|---|---|---|---|---|
| AI-generated artwork | ★★★★★ | ✖ invents bunkers and trees | ✖ no coordinates | low |
| Flat perspective-warped map | ★★ | ✔ | ✔ | very low |
| **2.5D terrain render from real data** (recommended) | ★★★★ | ✔ | ✔ by construction | low–medium |
| Full live 3D engine | ★★★★ | ✔ | ✔ | high (battery) |

**Recommendation: a data-driven 2.5D renderer.**
1. **Build step, on the Mac/workspace.** For each hole, a script turns the verified outlines, the lidar elevation and the lidar-derived tree positions into a "hole package". It contains:
   - a painted ground texture: fairway mowing stripes along the playing line, rough, sand with lip shading, water, paths
   - a height grid
   - a list of tree positions
2. **On the phone.** A small WebGL view drapes that texture over the height grid and stands tree sprites at their real positions.
   - It has two saved cameras: **Tee view** (behind the tee, looking at the green) and **Approach view** (closer, tilted to the green complex).
   - Everything is drawn in **one local metre grid per hole**, the same kind of frame the greens already use.
3. **Overlays.** Your GPS dot, the green front/center/back and bunker markers go through exactly the same projection as the artwork, so they cannot drift apart.
4. **AI imagery may be used only for surface textures** (grass, sand, tree sprites), never for shapes or positions.
5. **Battery fallback.** A pre-rendered still of each camera view, with the same projection data, so markers still line up.

## 6. GPS distances

**Green: FRONT | CENTER | BACK.** Same method as today: along the line from you through the green center, ported verbatim and tested for identical results.

**Bunkers and water (proposed method):**
- **Which hazards:** those ahead of you (in front of you along the hole) and within about 40 yd either side of your line to the target. The target is the green, or the dogleg point while you're still before it.
- **Reach:** where the line from you through the hazard's middle first enters the outline.
- **Carry:** where that line leaves the outline at the far side.
- **Side:** left or right of your line to the target.
- **Hazards that cross your line** (like Hole 2's pond) are measured along your line to the target instead.

Example from the *unverified* Hole 2 map, from the back tee:

| Feature | Reach | Carry |
|---|---|---|
| Green front / center / back | 442 / 457 / 472 | |
| Left greenside bunker | 421 | 437 |
| Right bunker | 475 | 483 |
| Pond, along the line | | about 46–73 yd short of green center |

**Uncertainty:**
- Phone GPS is typically ±3–5 yd in the open, worse under trees. The app already shows the accuracy reading.
- Mapped outlines add about ±1–2 yd once verified.
- V3 shows the accuracy and dims the numbers when it is worse than ±10 yd.
- It can optionally add a safety margin to carry numbers ("Carry 212 · +5 for GPS"). That's your choice.

## 7. V3 structure: built to become production later

```
Pocasset_Caddie_V3/                (local git; later the pocasset-caddie-v3 repo)
  index.html                       one page; all paths relative, so it runs from any address
  app/
    core/      state, view switching, settings
    storage/   the only module that writes; enforces the pocasset_v3: prefix
    gps/       GPS service (V2.3.1 "stays on" behaviour) + simulated GPS for testing
    geo/       projections, front/center/back, hazard reach/carry (ported + tested)
    scoring/   scorecard, putts, notes, CSV (ported)
    pins/      EZLocator entry + pin-sheet loading
    views/flyover/   2.5D renderer (independent component)
    views/green/     approved green display (verbatim port; images untouched)
  data/  course.json (pars, tees), holes/holeNN/ (outlines, height grid, trees, provenance)
  greens/  approved images (checksum-locked copies)
  sw.js    cache prefix pcv3-
  tools/   build scripts (extract hole, build hole package, lidar processing)
  tests/   unit tests, iPhone simulation tests, isolation test, green-integrity test
  docs/    DATA_SOURCES, DECISIONS, FILE_INVENTORY, CHANGELOG
```

- No framework and no build step for the app itself.
  - It uses plain JavaScript modules, plus one pinned copy of a small WebGL library stored in the repository, so it works offline.
  - That keeps it easy to maintain from any computer, or with any AI tool.
- **Later switch to production:** because V3 uses relative paths and its own storage prefix, it can be copied into the `pocasset_caddie` repository unchanged, or the old address can point to the new one.
  - An "Import from V2" step brings your round and pins across.
  - That happens only when you decide.
